**TDD (Test-Driven Development)** inverte a ordem natural: o teste vem PRIMEIRO, o código DEPOIS. Parece estranho — até você perceber que o teste define o comportamento esperado antes da implementação. É a metodologia favorita da indústria para código que não quebra.

> **Por que importa?** "Você pratica TDD?" é pergunta comum em entrevistas senior. E o ciclo RED-GREEN-REFACTOR é o vocabulário que todo time usa.

## O ciclo RED → GREEN → REFACTOR

```
RED    → escreva o teste ANTES do código → ele FALHA (função não existe)
GREEN  → implemente o mínimo para o teste PASSAR
REFACTOR → melhore o código sem quebrar o teste (ele garante!)
```

```python
# 1. RED — teste primeiro (a função ainda não existe!)
def test_calcular_desconto():
    assert calcular_desconto(100, 10) == 90.0
#    ↑ NameError — função não existe. RED.

# 2. GREEN — implemente o mínimo
def calcular_desconto(preco, percentual):
    return preco * (1 - percentual / 100)

# 3. REFACTOR — valide inputs, adicione edge cases...
def calcular_desconto(preco, percentual):
    if percentual < 0 or percentual > 100:
        raise ValueError("percentual invalido")
    return preco * (1 - percentual / 100)
```

## Por que escrever o teste primeiro?

1. **Define o contrato** — você decide o comportamento esperado antes de implementar
2. **Garante cobertura** — o teste existe porque a função nasceu dele
3. **Refatorar sem medo** — o teste avisa se o comportamento mudou

## Resumo

- **RED**: teste falha (função não existe) — o comportamento esperado
- **GREEN**: implemente o mínimo para passar
- **REFACTOR**: melhore com o teste como rede de segurança
- **Validação de input**: raise ValueError para entrada inválida
- TDD = código nasce testado
